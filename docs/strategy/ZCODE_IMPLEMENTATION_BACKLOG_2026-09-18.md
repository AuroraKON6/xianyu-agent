# Zcode 工业化执行工作包

日期：2026-09-18。状态：待执行的开发计划，不是交付报告。

配套：[产品与架构总计划](INDUSTRIAL_AUTONOMOUS_XIANYU_MASTER_PLAN_2026-09-18.md)、[来源核验](../research/INTEGRATION_EVIDENCE_2026-09-18.md)。

## 1. 执行约定

- 总负责人是用户；Zcode 负责实现、测试、证据和问题升级。AI 可以准备资料、分析、提出决策，不能伪造平台回执、用户授权或真实订单。
- 本轮目标是国内闲鱼经营系统；不合并跨境账本，不恢复 OpenClaw，不重新实现已经存在的聊天事件、价格承诺、商品事实和回复追踪。
- 路径以下均相对 `E:\闲鱼\xianyu`。标记“拟新增”的模块是建议落点，先查代码，存在等价实现就复用。
- 每个工作包独立提交；不回滚用户修改。数据库迁移必须有备份、兼容期和回退说明。
- 初始只开发离线、仿真和只读功能。写平台操作继续使用既有唯一执行路径；自动授权能力验收前不绕过人工审批。
- 所有外部数据标注来源、获取时间、有效期、账号范围。不可将演示、猜测、缓存过期值写成实时事实。
- 本次看到交接记录的 1026 个测试通过是历史结果；第一步重跑并保存当前结果，不直接照抄。

## 2. 工作包依赖和交付节奏

```text
WP00 -> WP01 -> WP03 -> WP05 -> WP06 -> WP09（第一条可视化商机闭环）

WP01 + WP10 -> WP13
```

阶段一先交付报价资料导入、同款匹配、贡献利润计算和决策卡。阶段二才接持续监控、多代理和授权影子运行。阶段三做交易、履约、账务闭环。不是先花数周重写 UI，再发现供应链不能成立。

估算按一名能审查代码的执行者、可获得必要账号资料计算，是排期预算不是保证；外部申请等待另算。整体建议 12-16 周工程建设，再用 4-8 周真实业务观察验证，允许按证据调整范围。

## WP00：锁定真实基线（1-2 天）

输入：当前仓库、`PROJECT_STATUS.md`、`ZCODE_HANDOFF.md`、测试命令、部署配置。

操作：
1. 记录 HEAD、工作区差异、Python/Node/Pi 版本、依赖锁定情况、现有路由和后台任务。
2. 运行隔离测试；所有失败列出测试名、错误、复现步骤。判断“预存”必须与相同环境的基线比较，不凭描述。
3. 核对 GH-04/05：聊天事件去重、价格承诺、事实版本和回复追踪的实际调用路径。
4. 对照注册器、调度器、Pi RPC，区分逻辑角色、真实进程、持久任务和仅日志循环。
5. 核对本地第三方项目来源、许可证、提交版本；统一现有 8/9 个 skill 的文档差异。

产物：拟新增 `docs/acceptance/BASELINE_2026-09-18.md`，附命令、退出码、脱敏日志和功能矩阵。

验收：任何“已完成”均能定位代码与测试；写操作测试不触碰真实账号。回退：文档和测试报告不改变运行行为。

## WP01：业务契约与存储接口（3-5 天）

拟新增：`xianyu_agent/commerce/contracts.py`、`repositories.py`；迁移工具选择先写 ADR。

契约至少包括 OfferSnapshot、ProductMatch、Opportunity、AgentJob、DecisionRecord、OperatingMandate、AuthorizationRecord、BudgetReservation、ProcurementOrder、LedgerEntry。

要求：
- 金额用 Decimal 和币种，时间用带时区的 UTC；业务日界线明确为 Asia/Shanghai。
- 区分 unknown、0、not_applicable；金额未知不能默认免费。
- 所有记录带业务范围、账号、schema_version、revision、source_ref 和关联 trace_id；供应商报价可独立于销售账号，但绑定用途明确。
- 定义 repository 协议，保持既有 JSON/SQLite 路径可读；新模块不得直接散落读写旧文件。
- Postgres 为生产目标，SQLite 用于单机 Alpha/测试；一次只选一个生产事实源，不永久双写。

测试：金额小数、跨日、版本冲突、账号隔离、序列化往返、空值与缺失值。回退：新功能默认关闭，旧业务不依赖新表存在。

## WP02：数据源资格与能力验证（2-4 天开发，外部等待单列）

拟新增：`xianyu_agent/providers/base.py`、`capabilities.py`，来源登记表。

每个来源记录：官方/第三方/文件、账号资质、API 权限、费用依据日期、配额、分页、报价字段、SKU 粒度、运费、库存、有效期、限流、条款和数据可保留范围。

先验证供应商文件通道，再验证 PDD 多多进宝的当前申请条件，最后决定 1688。不要凭 2021 年免费 API 文档编造当前权限。无凭证仍可做适配协议与脱敏样本测试。

验收：每个来源状态是 VERIFIED / PARTIAL / BLOCKED / REJECTED；有资格的来源抽样 20 个真实 SKU，记录原始响应摘要与实际缺失字段。没有真实请求就写 UNVERIFIED，不能算接入成功。

退出条件：申请一周无进展，保留阻塞原因，继续文件报价闭环；不无限堆爬虫绕过权限问题。

## WP03：供应商资料导入与 AI 辅助整理（3-5 天）

复用 `commercial_alpha_intake.py` 的证据检查，不新建一套互不兼容的证据体系。拟新增 `supplier_import.py`。

实现两步：preview -> confirm。第一版支持 CSV/XLSX 和人工粘贴结构化文本；图片/PDF/OCR 后续追加，不阻塞第一版。

preview 展示原值、建议字段、单位换算、置信度、缺失项、重复项和原文定位；AI 只能建议映射，不自行补库存/运费/授权。confirm 使用 preview_id、源文件 hash 和 revision，防止预览后文件变化。

测试：同文件重复导入、同 SKU 新版本、整箱/单件误差、阶梯价格、包邮条件、负数、公式单元格、重复表头、文件大小与编码、半途失败回滚。

验收：一份有来源的报价资料可以生成 OfferSnapshot；无法确认的内容停留草稿。回退：导入批次可标记撤销而不删除历史引用。

## WP04：报价采集与新鲜度管理（3-5 天）

拟新增 `providers/supplier_file.py` 和验证通过后的单一在线适配器；不预先承诺 PDD/1688 SDK 名称。

统一查询结果与错误码；实现超时、指数退避与抖动、Retry-After、分页断点、配额计数、熔断、凭证过期提醒、最后成功时间。重试仅限可安全重复的读取。

每次采集写不可变快照；同一来源报价更新不能覆盖历史订单成本。来源 pdd/pinduoduo 等别名在边界规范化。

测试：429/401/5xx、空页、重复页、部分 SKU 缺失、价格变化、断网恢复、过期缓存。验收：面板能区分实时/历史/过期/失败；过期数据不驱动自动承诺。

## WP05：同款与规格匹配（4-6 天）

拟新增 `product_matching.py`，RapidFuzz 只用于召回；LLM 给解释与候选，确定性约束负责排除型号/规格不符。

匹配等级：EXACT、COMPARABLE、NOT_MATCH、UNKNOWN。硬约束包括品牌型号、尺寸材料、数量单位、成色、保修、含税、交货范围；二手与全新不能只凭标题判同款。

建立至少 100 对人工标注样本，含困难负例和常见单位歧义；训练/调参集与保留验收集分开，记录数据版本。

验收：保留集 EXACT 精确率至少 95%，同时报告样本数和召回率；错误匹配进入复核，不把 95% 解读成可无条件自动采购。高金额品类允许更严格阈值。

回退：只展示候选匹配，关闭自动比较与采购动作。

## WP06：贡献利润与商机引擎（4-6 天）

拟新增 `unit_economics.py`、`opportunity_service.py`；复用 `resale.py` 的评分，不把“高分候选”直接等同“有利润订单”。

计算采购、首程运费、包装、平台/支付费用、安装、退货期望损失、税费预留和每单可归因成本。佣金仅在资格与回款明确时计入，券后价必须满足购买者条件。

输出基准/保守/压力情景、最低可售价格、盈亏平衡、现金占用、证据缺口。成本缺失时输出区间或 UNKNOWN，不填零凑利润。

状态：discovered -> researching -> ready_for_test -> testing -> validated/paused/rejected；状态转移带理由和证据，不能因为模型说好就 validated。

测试：运费不包偏远、采购阶梯最小起订量、退货、部分退款、满减摊分、价格有效期、币种与精度。验收：可手算复核的黄金样例全通过；机会卡可以追溯所有计算输入。

## WP07：持久子代理任务与决策记录（4-7 天）

改造入口：`agent_registry.py`、`agent_scheduler.py`；拟新增 `agent_jobs.py`、`decision_records.py`。保留现有业务 handler，不把名字注册当成真正工作流。

任务字段：UUID、parent_job_id、account_id、role、input_revision、status、priority、attempt、lease_owner/expires_at、heartbeat、deadline、token/cost_budget、cancel_reason、artifact_refs。

状态：queued/running/waiting_input/succeeded/failed/cancelled/unknown。原子认领、租约续期、异常回收；单账号写操作串行，读任务按配额并行。

决策卡记录摘要、备选项、证据、约束检查、模型版本、调用成本、授权来源与结果，不要求或保存模型隐含推理链。

测试：双 worker 竞争、进程在保存前后退出、租约过期、取消、重复消息、旧 revision、预算耗尽。验收：重启后任务可恢复；不宣称网络写操作天然 exactly-once，依靠业务幂等和 UNKNOWN 对账。

## WP08：Pi 运行器与插件验证（2-4 天）

基于现有 `pi_runtime.py`、`.pi/extensions/xianyu-ops.ts`；先锁定 0.84.2 基线，不因为插件报错直接全局升级。

用短期实验验证 pi-subagents：安装来源、许可证、版本、异步结果、取消、工具范围、会话隔离、token 预算。实验失败则以官方 RPC/SDK 独立会话实现 runner；Python 队列始终管理事实状态。

第一批四个角色：发现、匹配、定价、客服；其余角色可先是确定性服务，避免十个代理同时消耗预算。

验收：真实模型运行一项无外部写入任务，输出落库后由面板读取；mock 与真实证明分开。测试错误 JSON、超时、工具异常、上下文串账号、模型供应商不可用。回退：单 Pi 操作者模式仍可用。

## WP09：总经理与代理决策面板（5-8 天）

改造 `server.py` 与 `web/app.js`：按业务域提取路由和前端模块，逐步替换，不全量重写。

视图：总览、商机、报价对比、代理任务、决策详情、关键审批、订单/售后、利润与复盘。每个列表能筛账号/状态/日期，点进记录再返回保留筛选。

提供 SSE 或受控轮询、分页、加载/空/错误/过期状态；禁止用固定数字装经营效果。审批展示真实受影响金额、商品、账号和证据版本。

验收：Playwright 桌面 1440x900 与移动 390x844，测试从导入到决策卡再到审批详情；截图无重叠，接口失败有重试，刷新不重复提交，SSE 断线能恢复。

不展示 hidden chain-of-thought；展示可解释的业务理由、工具事件和回执。回退：旧 console 保留入口直到等价流程通过。

## WP10：经营授权与影子运行（5-8 天）

拟新增 `operating_mandates.py`、`authorization_policy.py`、`budget_reservations.py`。

用户授权限定账号、动作、SKU/品类、单笔/每日金额、最低贡献利润、有效期、报价时效、允许模板、例外升级和撤销。系统不得伪装成人类审批；新增 policy 类型授权记录，关联用户签发的 mandate。

执行顺序：读取当前事实 -> 校验策略 -> 原子预留预算 -> 排队 -> 执行前重验 -> 调适配器 -> 对账后结算或释放。UNKNOWN 保留预留直到查清，不能盲目重试并释放额度。

先 shadow：只记录“本会自动允许/拒绝”，人工仍执行。验证至少 7 天、100 条建议；没有自然样本时延长，不用合成样本冒充线上。

测试：并发超额、午夜额度、撤销后已排队、价格/库存修订、授权过期、负数金额、部分成交、未知回执、账号错配。硬门禁绕过为零。回退：一个开关退回全人工审批，不丢已执行记录。

## WP11：客服与价格承诺（4-6 天）

复用 `chat_events.py`、`price_commitments.py`、`product_facts.py`、`auto_reply.py`、`/reply-trace`，具体模块存在性先核验。

知识来源是当前商品事实和报价，不是通用 prompt。先开放有版本依据的规格/发货说明；议价必须高于有效底价并符合授权，不承诺未知库存与到货日。

至少 200 个客服场景：否定句、引用对方价格、历史消息、运费不是售价、多件合计、多个 SKU、退款、重复事件、已人工接管、事实更新。金额抽取需同时判断说话者、语义与确认发送状态。

发送失败不能写成已承诺；人工接管立即停自动发送。关键误承诺/重复发送用硬测试零容忍，普通回复质量用人工标注评分。回退：只产草稿。

## WP12：上架、库存和小实验（4-6 天）

完善 listing 结构化字段，复用既有草稿/审批/执行；文案和图片权利、真实规格、价格阶梯、交付条件有证据。

移除未验证的“我方其他平台店铺”、返现等固定断言。发布后必须保存平台 ID 与回读结果；超时为 UNKNOWN，先查平台再重试。

供应商库存不是本店可售库存：定义分配、安全余量、库存过期、缺货暂停及订单锁定；第一版宁可低库存不超卖。

同商品多链接只做规则允许且可解释的实验，不把批量重复铺货当核心增长。一次控制一个主要变量，记录曝光是否真实可得，不伪造转化分母。

测试：价格改动后旧审批、重复发布、下架未知、库存为零、供应商库存过期、图缺失。回退：只出草稿，停自动变更。

## WP13：采购、履约、售后和利润对账（6-10 天）

复用 `order.py`/现有订单服务；拟新增 procurement、reconciliation、ledger 模块，按当前结构调整名称。

订单确认后重新核 SKU、供货、地址与成本，再产生采购单；首期付款和异常赔付人工确认。只有验证过的供应商订单接口才允许后续授权采购，不能以浏览器点击结果替代到账证明。

销售单、采购单、包裹、退款、费用分别建实体，支持一单多包、部分发货、换货和部分退款。账务记录 append-only，以冲正更正，不覆盖原支出。

利润分 expected/provisional/settled；签收不等于回款，售后未结不算最终利润。销售收入与采购支出必须关联真实流水或标记未对账。

验收：模拟并手工核对正常单、缺货取消、运损、退货、部分退款、超时未回款；后续至少一笔真实订单走到结算或完整关闭，再谈扩大经营。

## WP14：部署、恢复与可观测性（5-8 天，贯穿各包）

先选择单机运行目标：可保持 Windows 或迁至 Linux；浏览器账号迁移和 Pi 兼容性实测后再定，不默认容器内登录一定稳定。

生产使用版本化配置、健康检查、结构化日志、OpenTelemetry trace、调用预算和告警；Langfuse 可选，脱敏模型输入后才接。默认不增加 Redis/Temporal 等非必要服务。

数据库迁移演练：快照备份 -> 离线拷贝 -> 转换 -> 总量/金额/关联校验 -> 维护窗口切换 -> 只读核对 -> 开启 worker。失败恢复旧源；不得在新旧库各自执行订单。

备份：每日全量；若承诺 RPO 15 分钟，采用经验证的连续归档/增量或等效机制，不能只靠每日快照。目标 RTO 60 分钟，通过全新目录/实例恢复计时证明。

故障演练：断网、模型不可用、平台登录过期、磁盘满、worker 崩溃、数据库不可达、恢复后重复任务、错误版本回退。告警要关联影响订单和处置说明。

禁止未经用户同意恢复登录自启动和弹窗任务；运维启动必须静默、可见状态、可停止。验收包括至少 7 天稳定性观察和恢复报告，不用短测试冒充长期稳定。

## WP15：真实小规模经营验收（业务观察另计 4-8 周）

前置：技术基线、来源资格、准确 SKU、供应商履约、商品内容权利、真实账号、预算、人工值守、紧急停止全部具备。

顺序：一账号一 SKU 人工确认 -> 只读观察 -> 客服草稿 -> 低风险授权回复 -> 有额度的价格调整 -> 三 SKU。10-30 SKU 属于后续容量目标，不是第一批经营计划。

每次放量用独立 release 决策记录，写明证据与例外。业务指标：真实咨询、成交、取消、履约时间、退款、最终贡献利润、人工作业分钟；不承诺收入，不用刷单制造验收。

停止条件：错误商品/报价承诺、重复外部动作、授权越界、未知订单状态长期未解、来源失效、超过预算、售后负担失控。自动停止受影响动作，保留查询和人工处置能力。

最终验收：真实订单闭环、结算可核对、关键决策可追溯、人工能接管、备份可恢复。没有真实订单只可报技术交付通过、商业验收未通过。
