## 3. 业务顺序与判定

1. 按既有导入协议保留原始字节、预览并确认批次。来源种类、来源索引、原观察时间和截止时间必须在原报价与持久化快照中一致。
2. GET缺口，不把成功导入、供应商名字或本地文件存在视为真实性证明。
3. 补充供应商身份材料索引、来源使用许可、出具/收到/到期时间，以及逐快照的币种、计价/数量单位、运费目的地与分摊方式、库存证据和税务/交付/售后条款。
4. POST或CLI提供原始报价字节，实际重算SHA-256，与导入批次及声明双重匹配。
5. 拒绝撤销/部分失败批次、缺失或重复快照、跨供应商/批次绑定、demo改标、未来/无时区/过期时间、旧报价重新导入后冒充新报价。
6. 已知矛盾返回`blocked`；证据未知返回`needs_evidence`；资料完整最多是`ready_for_human_review`。人工核实真实性与授权后，才讨论下一阶段。

三个结果恒为false：`provider_verified`、`external_llm_authorized`、`platform_action_authorized`。提交者声明允许外部模型也不会自动解锁调用。报告摘要绑定当前输入，不是永久资格或审批令牌。

额外的身份/许可/售后资料检查尚未强制进入全部旧业务入口；本批明确为只读诊断，不宣称整个项目已经执行这些人工授权门禁。

## 6. 已覆盖的关键反例

- 仅声明正确hash但不提供文件、同长度原字节变更，均不能ready。
- 共享来源元数据demo/unknown、来源引用不符、延长已有到期日，不能被补充声明覆盖。
- 观察时间、取得时间、导入时间分开；收到时间可以晚于供应商观察时间，但不得晚于导入。
- 未知、未提供、NaN、负价格、布尔/小数MOQ、库存不满足MOQ、单位不明、运费范围不明不被自动猜成合格值。
- 每个snapshot独立要求库存时间、条款和材料索引；来源、批次、供应商和现有快照关系必须一致。
- 请求不能伪造operator、把字符串布尔转成授权、指定回拨评估时间或让服务下载URL。
- API超限、损坏存储、歧义批次、错误base64、未知批次均明确拒绝。
- CLI读入文件在检查间变化即失败；不存在的数据目录不创建；评估不改变业务文件，新实例/子进程重读结果一致。
- 即使结构齐全或声明允许模型，仍不授予模型/交易授权；真实应用挂载与现有任务会话403限制有隔离验证。
