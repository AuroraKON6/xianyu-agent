## 1. 实施事故与恢复（如实记录）

批中发生两次测试污染 live 数据，均已检测并**字节级恢复**（恢复后 247/247 哈希与开工清单一致）：

1. **事故 A（约 19:47–20:05）**：实施者多次直接 `python -m unittest discover` 运行测试，未走隔离入口。`.env` 的 DATA_DIR（指向 `data/live`）被加载，`data/live/commerce/agent_jobs.json`、`decisions.json` 被写入。
   - 恢复：9+7 条当日新记录按存储层序列化格式（`json.dumps(..., ensure_ascii=False, indent=2)` + CRLF）过滤重建；一条被 run_once 认领的 2026-10-12 旧任务按 `build_agent_job` 提交模式回滚字段（revision=1/status=queued/attempt=0/删除 lease_claimed_at+completed_at/error=None/cost=None）。两个文件的重建结果与开工基线 SHA-256 **完全一致**（256e5b2e…、57e251db…）。
   - 污染副本留存：`/tmp/contaminated-agent_jobs.json.bak`、`/tmp/contaminated-decisions.json.bak`。
2. **事故 B（约 19:58–20:01，同一根因）**：两条未带隔离环境变量的 discover 运行使 server 共享 PiTaskRunner 执行 quote-review 演示链，在 `data/live/commerce/` 新增 `model_usage.json` 与 4 个 `pi_evidence/job_*__attempt1.json`。
   - 恢复：5 个文件均为基线后新增（基线清单无此路径），直接删除；复核 247/247。
   - 该根因的工程含义已被 R01 吸收：此后所有直跑均显式携带沙箱环境变量，最终验收只认离线入口。

两起事故均属"绕过隔离入口的人为失误"，不是隔离机制失效；离线入口自身在全部运行中保持 live 数据零变更（before/after 指纹一致）。
