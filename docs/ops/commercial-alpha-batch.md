# Commercial Alpha 试运营批次

本手册定义从“系统可运行”到“同一账号完成第一笔可核算订单”的实际经营顺序。批次不是演示清单，也不允许人工勾选阶段完成；每个阶段必须由同一卖家账号、同一候选商品、同一平台商品 ID 和同一订单链路的本地证据自动推导。

## 1. 批次目标

首个批次只回答四个商业问题：

1. 供应商、商品资料和价格是否足以支撑真实发布。
2. 发布后是否产生达到目标数量的有效咨询。
3. 咨询是否产生真实付款订单，并能按承诺完成履约。
4. 扣除供应商成本、运费和平台费用后是否有可重复利润。

首批默认控制值：

| 控制项 | 默认值 | 经营含义 |
|---|---:|---|
| 候选上限 | 3 | 同一批次最多验证 3 个候选，避免研究范围失控 |
| 候选目标 | 3 | 达到后再从中选 1 个进入发布 |
| 发布上限 | 1 | 第一批只承担 1 条发布承诺 |
| 采购预算 | 1000 元 | 付款订单需要采购时可动用的最大现金 |
| 最大亏损 | 100 元 | 已实现利润达到 -100 元时要求停止决策 |
| 售后率止损 | 50% | 至少有 1 笔付款订单后，退款或纠纷比例达到阈值即停止 |
| 咨询目标 | 3 | 同账号、同平台商品 ID 的非重复咨询 |
| 付款目标 | 1 | 同账号、同平台商品 ID 的付款或后续状态订单 |
| 监控周期 | 14 天 | 到期必须复盘，不无限等待 |

## 2. 开批前准备

### 2.1 卖家账号

必须明确选择一个已启用的 `cookie_id`。开批后所有证据只归属于该账号，禁止用 A 账号的运行时状态和 B 账号的询盘拼成“已就绪”。

账号就绪需要同时满足：

- 账号已配置且启用。
- 账号 Prompt 配置完整。
- 商品和订单同步均为新鲜状态。
- 账号运行时已连接。
- Cookie 和 Token 证据仍在新鲜窗口内。
- 没有验证码、登录失败或未处理运行时错误。

### 2.2 候选商品

每个候选必须属于批次品类，并在进入发布前具备：

- 当前供应商链接和报价。
- 报价与库存的检查时间。
- 供应商发货能力与责任边界说明。
- 可使用的图片及图片权利证据。
- 非空规格参数。
- 目标售价、供应商成本、供应商运费、预估平台费用和退款率。
- 最低利润额和最低利润率均达到项目配置。
- 操作者明确批准候选。

### 2.3 供应商确认

发布前至少完成一次人工核对并记录：

1. 当前规格是否仍可下单。
2. 单件采购价和运费是否与系统一致。
3. 付款后最晚发货时间。
4. 是否可提供可追踪物流单号。
5. 缺货、破损、错发和退货分别由谁承担成本。

没有供应商确认，不进入草稿审批。

## 3. 十阶段证据链

| 顺序 | 阶段 | 通过证据 | 不计入的情况 |
|---:|---|---|---|
| 1 | `account_ready` | 指定账号的 7 项就绪条件全部通过 | 其他账号就绪、Stub 适配器 |
| 2 | `candidate_pool` | 批次内存在且品类一致的候选达到目标数 | 已删除候选、品类不一致的历史 ID |
| 3 | `publish_ready` | 至少 1 个批次候选通过商业发布前检 | 供应商、图片、规格、利润或账号证据不完整 |
| 4 | `approval_created` | 批次开始后创建的 `resale_listing` 工单，账号和候选精确匹配，并含 `publish_listing` 审批 | 批次开始前工单、其他账号或候选的审批 |
| 5 | `publish_confirmed` | 对应审批的执行任务完成，结果成功并返回真实 `external_id` | 空 ID、`stub_` 模拟 ID、失败任务、无关审批 |
| 6 | `inquiry_observed` | 发布完成后，账号和 `item_id` 匹配的非重复消息达到咨询目标 | 重复消息、发布前消息、其他账号或商品消息 |
| 7 | `paid_order` | 发布后，账号和 `item_id` 匹配的订单达到付款或后续状态，并达到付款目标 | 待付款、发布前订单、其他账号订单 |
| 8 | `fulfillment_observed` | 同一付款订单当前或历史状态到达已发货/已签收 | 只有采购记录但无平台履约状态 |
| 9 | `profit_reconciled` | `ResaleOrder.xianyu_order_id` 匹配付款订单、候选属于批次、状态完成且 `actual_profit` 可计算 | 手工估算利润、无订单 ID 关联、批次前订单 |
| 10 | `review_decision` | 监控期到期、触发止损或完成利润对账后，操作者记录复盘决策 | 开批早期的临时暂停或继续操作 |

系统只输出工单 ID、审批 ID、任务 ID、平台商品 ID、消息台账 ID、订单 ID、计数和时间，不输出买家 ID、消息正文、Cookie、Token 或 Prompt 内容。

来源明确以 `fake`、`stub`、`mock`、`test` 或 `demo` 开头的订单只保留在 OrderRuntime 的观察总数中，不计入真实待履约、售后、批次付款或利润证据。日仪表板分别显示 operational 与 synthetic 数量。

## 4. 实际运行顺序

### 第 0 天：建立批次

1. 打开控制台的 `Commercial Alpha 试运营`。
2. 从下拉框选择已启用卖家账号。
3. 输入单一品类。
4. 设置候选、发布、预算、亏损、售后率、咨询、付款和监控参数。
5. 创建批次。
6. 按“下一步”只处理第一个未通过阶段。

创建批次不会自动发布、发消息、下采购单、发货或退款。

### 第 1 至 2 天：建立小候选池

1. 只添加与批次品类完全一致的候选。
2. 每个候选完成供应商与商业证据记录。
3. 查看发布前检结果。
4. 淘汰无法在 24 小时内补齐证据或利润不足的候选。
5. 只让最强的 1 个候选进入发布审批。

候选数量达到上限后停止继续搜集，先完成验证。

### 第 2 至 3 天：审批与发布

1. 在批次候选上创建上架草稿。
2. 系统先检查生命周期、止损、发布承诺、重复候选和剩余采购预算。
3. 通过后创建唯一的 WorkOrder 和待审批 `publish_listing`。
4. 操作者检查标题、首图、规格、价格、交付、售后说明和账号。
5. 批准后进入 ExecutionJobQueue。
6. 执行任务只有拿到真实平台商品 ID 才算发布成功。

待审批发布已经占用发布上限。重复点击不会生成第二份发布承诺。

### 第 3 至 14 天：咨询与订单

每日开工检查：

1. 账号运行时是否仍就绪。
2. 是否出现执行失败或验证阻断。
3. 新咨询是否已进入 MessageIntake。
4. 待发送回复是否完成审批。
5. 是否出现待付款、已付款、待发货或售后订单。
6. 批次是否触发任何停止原因。

发布已占满时不再创建新草稿，先观察标题、价格和回复是否产生咨询与付款。

### 付款后：采购与履约

严格按以下顺序处理：

1. 确认平台订单状态已经付款。
2. 核对买家所选规格、数量和收货信息。
3. 在批次的“付款后履约”填写数量和脱敏收货地摘要，并确认规格、地址、供应商库存和报价四项核对。
4. 系统验证订单必须来自该批次账号和已发布商品，并检查预计采购敞口不超过批次预算。
5. 系统用 `commercial_trial:{trial_id}` 获取订单履约锁，防止重复采购或重复发货。
6. 系统创建 `resale_purchase` 工单和 `prepare_purchase_draft` 审批；重复提交返回原交接，不创建第二份审批。
7. 操作者批准采购草稿后，系统只生成手工采购任务，不会自动付款或向供应商提交订单。
8. 操作者在供应商处手工下单，记录供应商订单号和物流单号，并创建订单对账记录。
9. 平台订单同步到已发货、已签收、售后或关闭后，才能在批次中释放履约锁。

采购审批被拒绝时不会计入履约采购承诺，批次会把该订单列为最高优先级处理项。此时可以直接释放履约锁，但必须继续决定关闭/退款还是改走人工履约；系统不会把被拒绝的采购记成已履约。

不得在买家付款前产生供应商采购支出。采购预算按供应商成本加供应商运费计算，不按销售额计算。

采购草稿、采购任务和 ResaleOrder 会继承 `commercial_trial_id`、闲鱼订单 ID、卖家账号、平台商品 ID 和履约锁 owner。批次台账只保存这些审计字段，不保存买家姓名、完整地址或消息正文。

### 订单结束：利润对账

必须记录：

- 闲鱼订单 ID。
- 批次候选 ID。
- 实收销售额。
- 供应商采购成本。
- 供应商/履约运费。
- 平台费用。
- 退款、补偿和其他售后损失。
- 最终 `actual_profit` 和利润率。

只有状态完成且订单 ID 精确关联的 ResaleOrder 才能完成利润阶段。

## 5. 止损规则与动作

| 原因代码 | 触发条件 | 立即动作 |
|---|---|---|
| `exposure_exceeds_cash_budget` | 已付款订单的实际采购成本超过预算 | 暂停新采购，核对订单与成本录入，做停止决策 |
| `committed_cash_exceeds_budget` | 发布承诺对应的最低备货需求超过预算 | 不创建新草稿，降低发布范围或提高预算后重开批次 |
| `procurement_commitment_exceeds_budget` | 已创建的履约采购交接超过预算 | 不批准采购，复核数量、报价和订单关联 |
| `realized_loss_exceeds_max` | 已实现利润小于等于负的最大亏损 | 停止放量，逐单复盘成本、退款和定价 |
| `after_sales_rate_exceeds_threshold` | 至少 1 笔付款订单且售后率达到阈值 | 停止新发布，处理现有售后，检查供应商和描述偏差 |
| `account_lost_readiness_after_commitment` | 已有审批/发布后账号失去就绪状态 | 暂停执行，恢复登录、同步和运行时后再决定继续或停止 |

触发止损不会自动取消订单、退款或删除商品。系统阻断新的批次草稿，并要求操作者选择停止、暂停或在完成调查后继续。

## 6. 复盘决策

允许的决策：

| 决策 | 适用场景 | 后果 |
|---|---|---|
| `continue` | 临时问题已排除，仍在监控期 | 批次恢复运行；仍受原上限和止损约束 |
| `pause` | 等待供应商、账号恢复或补证据 | 阻断新批次草稿，可恢复 |
| `stop` | 商业假设失败或止损不应继续 | 批次终止，不可恢复 |
| `complete` | 监控期已满或利润已对账 | 批次完成，不可恢复 |

完成后生成本地 Markdown 报告，至少回答：

1. 哪个候选被发布，平台商品 ID 是什么。
2. 产生了多少有效咨询和付款订单。
3. 履约是否按承诺完成。
4. 真实采购敞口和已实现利润是多少。
5. 是否出现售后、账号或执行阻断。
6. 下一批应继续、调整品类、调整价格，还是停止。

## 7. API

| 方法 | 路径 | 作用 |
|---|---|---|
| `POST` | `/commercial-trials` | 创建批次 |
| `GET` | `/commercial-trials` | 查看全部批次及实时证据 |
| `GET` | `/commercial-trials/active?cookie_id=...` | 查看指定账号活动批次 |
| `GET` | `/commercial-trials/{trial_id}` | 查看单个批次 |
| `POST` | `/commercial-trials/{trial_id}/candidates/{candidate_id}` | 添加同品类候选 |
| `POST` | `/commercial-trials/{trial_id}/candidates/{candidate_id}/listing-draft` | 通过批次门禁创建草稿和审批 |
| `POST` | `/commercial-trials/{trial_id}/orders/{order_id}/fulfillment-handoff` | 对精确匹配的付款订单加锁并创建采购审批 |
| `POST` | `/commercial-trials/{trial_id}/orders/{order_id}/fulfillment-release` | 平台已发货或关闭后释放履约锁 |
| `POST` | `/commercial-trials/{trial_id}/decision` | 记录继续、暂停、停止或完成决策 |
| `POST` | `/commercial-trials/{trial_id}/report` | 生成本地复盘报告 |

旧 `/trial-run/*` 接口仅保留兼容，不再作为 Commercial Alpha 经营进度来源。
